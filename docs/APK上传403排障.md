# APK 上传 403 排障说明

## 1. 现象

`assembleRelease` 正常完成，但 `uploadReleaseApk` 返回：

```text
curl finished with non-zero exit value 22
```

实际 HTTP 响应为：

```text
HTTP/1.1 403 Forbidden
```

## 2. 已排除的原因

- Android 侧上传 URL 已经正确：

```text
http://116.236.16.218:8001/UploadApk.ashx?fileName=app-release.apk
```

- GET 请求能到达 Handler，返回 `405 Method Not Allowed`，说明 IIS Handler 已经部署。
- 上传 5 字节测试文件同样返回 403，说明不是 APK 文件太大。
- 认证能通过 IIS 层，问题不是 `--anyauth --user` 参数。

因此当前问题是服务端 Handler 在执行写文件时被 IIS 拒绝，而不是 Android 构建脚本问题。

## 3. 服务端排查步骤

### 3.1 确认站点和路径

1. 确认站点根目录。
2. 确认站点根目录存在 `UploadApk.ashx`。
3. 确认 `Download` 目录存在，且 `UploadApk.ashx` 使用：

```csharp
context.Server.MapPath("~/Download/")
```

如果 Handler 部署在 `/Download/UploadApk.ashx`，而 Android 请求的是 `/UploadApk.ashx`，请统一使用站点根目录：

```text
/UploadApk.ashx
```

### 3.2 检查 IIS 应用池身份权限

查看站点使用的 Application Pool：

- 确认应用池 Identity。
- 给应用池身份授予物理 `Download` 目录的“修改”权限。

通常需要授权：

```text
IIS AppPool\应用池名称
IIS_IUSRS
```

至少需要：

- 读取和执行
- 列出文件夹内容
- 写入
- 修改

### 3.3 检查 Windows Authentication 和调用身份

如果启用了 Windows Authentication，当前上传账号需要：

- 能访问站点。
- 能访问 `Download` 目录。
- 如果 Handler 没有启用 `impersonate`，实际写文件权限由应用池身份决定。

### 3.4 使用新版 Handler 查看真实异常

已经更新本地模板：

`tools/iis-upload/UploadApk.ashx`

新版本捕获 `SaveAs` 异常并返回 500 和详细错误：

```text
Upload failed: ...
```

将此文件重新部署到 IIS 站点根目录，再次上传即可看到具体错误。

## 4. 为什么之前能成功

之前的成功很可能是以下之一：

- 服务器 `Download` 目录曾经允许 IIS 应用池身份写入。
- 上传账号曾经有目录写权限。
- IIS 站点或 Application Pool 配置后来被调整，导致权限变化。
- `UploadApk.ashx` 或 `web.config` 在服务器上被重新发布，导致 Handler 路径或权限发生变化。

Android 端当前 Gradle 上传逻辑已经恢复为可用状态，不需要再改本地构建脚本。
